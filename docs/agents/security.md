Money-flow as written: `POST /api/orders` (gateway) → order-service: price from catalog → `payment-service POST /` (create intent, key `order-{orderId}-{crypto.randomUUID()}`) → compare `intent.amount` vs order total (±$0.005) → `auth-service /verify-otp` (consumes code) → `payment-service POST /capture` (marks succeeded; idempotent) → push order → fire-and-forget receipt email.

Note: `payment-service` is an in-memory stub today (intent + flag flip, no card processor wired). The ordering above is what a real provider integration would inherit.

## Direct answers to the review questions

- **Double-charge: can two captures happen for one payment?** No. `/capture` is idempotent and atomic; a second capture of a `succeeded` intent returns 400. The order-service captures exactly once per order, after the OTP is consumed. The residual double-charge vector is client retry semantics (row 2).
- **Who can call `/capture` directly?** Browser: no (gateway does not expose payment-service). Docker-network peers: yes (it binds `0.0.0.0`, `expose 3006`). The order-service by design.
- **Can the order-service be tricked into capturing a different intent?** No — the client cannot set `paymentIntentId` (ignored at the edge); the order-service always captures the intent the payment service returned; a pre-captured intent makes `/capture` return 400 → order 503, no charge.
- **Fingerprint includes `orderId` — help or hurt dedup?** Neither today (keys are unique per attempt). It correctly rejects same-key-different-order with 409; if keys are ever reused, it prevents returning another order's intent. The `email:key` map key is mildly ambiguous (colon-in-email edge), but the fingerprint (which includes `metadata.email`) turns any collision into a 409, not a leak.
- **attempt-id guessability / cross-user replay / owner check:** there is no client attempt id. If one is added later: keys are `crypto.randomUUID()`-based (unguessable); map is scoped by email; no enumeration (no GET route); dedup result ownership should be checked (`stored.email === sessionEmail`) before `verifyCheckoutOtp` (see row 5).
- **OTP brute force / ordering / races / logs:** bounded (5 guesses per code row, 5/min per recipient, 10/min verify-otp per IP+email); code consumed before capture; concurrent verify is atomic (sync handlers); OTP not logged in prod (dev-mode exception, row 9).
- **CAPTURE race:** no attempt ids exist; concurrent `POST /api/orders` = two orders by design; capture idempotency means no double-capture of one intent.
- **Notifications open relay:** historical token committed (rotate production per §1 of `DEPLOYMENT-SECURITY.md`); current tree is fail-closed with constant-time compare + rate limit.
- **Gateway:** case-insensitive routing handled (tiers are matched on `toLowerCase`); only auth/catalog/cart/orders are proxied, so no alternate path to payment/notification through the gateway.

## Operational footnote

`docker-compose.yml` does not set `AUTH_SERVICE_URL` for `cart-service` (default `http://localhost:3002`). In Docker that resolves to the cart service itself, whose `/me` is 404 → `sessionEmail()` → null → 401 on every cart route. Works in dev on a single host; a deployment bug worth fixing (point it at `http://auth-service:3002`).
